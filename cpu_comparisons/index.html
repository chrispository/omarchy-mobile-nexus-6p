CPU SPECS ≠ PORT CONFIRMATION
What do “angler”, “oriole” and “cheetah” mean?

They are device codenames: short identifiers used in kernel device trees, build targets, firmware packages and porting notes. They identify a phone or board, not its CPU architecture or performance. For example, a guide for cheetah targets the Pixel 7 Pro; it does not automatically apply to every Tensor G2 device.

01 / INSTRUCTION SET

Most roads lead to ARM64.

AArch64 is the 64-bit execution state used by ARMv8 and ARMv9 phones here. A newer core does not need a different distro image just because its name changes. ARMv7 needs a 32-bit userland; Intel needs x86 packages.

02 / MICROARCHITECTURE

Core names tell another story.

Cortex-A53, Cortex-A78, Cortex-X1, Samsung M3, and Apple Hurricane are different CPU implementations. Kryo names can describe modified Arm designs. Core counts and bar lengths here are hardware facts, not benchmark scores.

03 / THE PORTING UNIT

Target the SoC, then the board.

Tensor G2 sharing makes Pixel 7 the closest move from 7 Pro. Matching CPU cores alone does not share display controllers, firmware, boot chains, or power management. Every board still needs validation.

01 / REUSE WHAT YOU HAVE

Pixel 7 → Pixel 6

Pixel 7 shares Tensor G2 / gs201 with the working 7 Pro port. Panel, touch, and battery differences still need board work. Pixel 6 is the next related platform: gs101 has upstream groundwork and local community bring-up.

More same-SoC targets: Pixel 7a and Pixel Fold. Fold already has a partial local port; two displays add complexity.

02 / ANOTHER PROVEN LINUX BASE

OnePlus 6 / Fairphone 4

Both have community ports with mainline-oriented kernels and accelerated graphics. That reduces driver discovery, but Arch Linux ARM packaging, Omarchy integration, suspend, and telephony still need validation.

PinePhone Pro is useful for another SoC family. The original PinePhone is a Linux reference, but its old Mali-400 GPU is a poor match for a modern Hyprland desktop.

03 / FINISH THE OWNED HARDWARE

Nexus 6P → Nexus 5X

Your local notes already record Omarchy’s shell on Nexus 6P via simpledrm and software rendering. Later notes enable the A53 cluster; A57 power management and accelerated graphics remain substantial work.

Nexus 5X uses the closely related Snapdragon 808 and the same A57/A53 core designs. Shared SoC groundwork helps; it does not make the 6P image transferable.

The Apple question

Same instruction set.
A different way in.

Native Arch on Android phones? Yes—the local 7 Pro and 6P work already demonstrates that path. Native Arch on an iPhone? Plausible research, with a much steeper desktop integration gap.

M-series Mac work helps, but doesn’t make an iPhone an Asahi target. Asahi’s device list covers Macs. Its bootloader and reverse-engineering knowledge can be reused, but iPhones have different boot policies, peripherals, and GPU generations. Even an M-series iPad is not automatically supported because its chip also appears in a Mac. Asahi device list ↗

Older iPhones can already boot Linux. Sandcastle established an Android/Linux route. The current community generic iDevice port lists tested A7–A11-era devices, including iPhone 6, 7, 8, and X, using an exploit-assisted, tethered boot path. The generic matrix still lists broken 3D acceleration and audio; the iPhone 7 page reports some additional device-specific functionality. A console boot does not establish Hyprland readiness. Community iDevice status ↗ · Sandcastle source ↗

My assessment: an Arch Linux ARM root filesystem is a plausible experiment once the exact phone’s kernel, boot method, and userspace page-size compatibility are solved. A usable Omarchy phone also needs KMS/display, GPU acceleration, input, charging, and sleep. Start with the iPhone 7 as a research device; Android candidates with established Linux graphics are more productive expansion targets.
